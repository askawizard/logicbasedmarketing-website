Case studies / Lead routing and identity

Leads routed by source, and ownership that stays where it lands

Inbound leads fell through to one default owner, leads kept changing owner after they were taken, and a phone match could merge a stranger onto a real customer. I rebuilt routing by source, traced the ownership loop to an integration with an 8 of 8 match, and closed the identity and booking gaps behind it.

A B2B industrial equipment company selling by web, phone and dealers, with demand arriving through phone calls, an answering service, web chat, paid search and booking links. I owned the lead intake integrations and the sales console; routing changes went live with the owner's sign-off. Diagnosed and built every fix myself: the routing package, the live tests and field-history proof, the executive brief, the console header fix, the merge veto and the chatbot booking gates.

The problem

The active lead assignment rule had exactly one entry, so everything it did not match fell through to the org's default owner: 1,219 of 1,395 leads in 60 days landed on one person regardless of source. Leads a rep took were moving back to another owner about a minute later, and the audit trail pointed at the wrong person. Separately, a lead-merge sweep had no email-conflict check, so a phone-only match could put a spam caller's number onto a real customer's contact and quote PDF, and the website chatbot could book a call with no number to dial.

What I built

I routed phone-originated, answering-service and booking sources to the second sales rep and left chat, paid search, SEO, email and web forms with the owner. Salesforce will not accept assignment-rule changes through the ordinary metadata call, so I deployed the rule as a zipped Metadata API package with idempotent apply and revert scripts, and used contains conditions because several source values integrations write are not in the picklist.

For the loop I tested the obvious explanations against the live org with disposable leads and eliminated them one by one. The cause: Salesforce re-runs the assignment rule on every API edit to a Lead unless the caller sends Sforce-Auto-Assign: FALSE, and a third-party integration was editing leads all day. I switched on owner field history to prove it, wrote a two-page brief with the one-line fix, and fixed the same defect inside our own console so updates never re-route and a rep's own lead stays with the rep who quoted it.

On identity, both merge routines now apply an email-conflict veto with a name-match override, and email-less call leads still merge on phone. The chatbot now captures a number typed anywhere in the chat, refuses to book without a dialable number, and strips placeholder contacts before they reach Salesforce.

Decisions that mattered

  • I read the owner back after every change, because a Lead owner PATCH can return HTTP 204 and still silently revert the owner.
  • The brief placed the cause on the integration, not the person, and stated plainly that one day of history identifies the cause but not how long it had been running.
  • I only ask for a phone number when none is on file, since 118 of 121 recent bookings already carried a real number.
  • Email-less leads still merge on phone, so the veto fixed the crosswire without breaking the inbound-call path that worked.

How the result was checked

The new routing was verified live with five disposable test leads. The loop was proven with owner field history: in the first day the rule took 8 leads that had an owner, and all 8 had the integration logging in within the same minute. A read-only 180-day audit found 7 phone-matched, email-mismatched conversions: 5 were one person with a typo and 2 were genuine crosswires. The chatbot suite ran 29 scenarios with 0 errors, 0 gate blocks and 0 redundant asks.
