Case studies / Reliability engineering

Made every failure loud, and found four dead jobs dashboards called healthy

A sync error that only reached a log file showed failures could sit unnoticed for days, and later the health monitor reported QuickBooks healthy during an API outage. I made every caught error alert a person, built a monitor that heals common breaks on its own, then swept 29 production services and restored four jobs that had been dead while every status screen said otherwise.

A B2B industrial equipment company whose order, accounting and reporting automation runs as cloud services and scheduled tasks connected to QuickBooks, WooCommerce, ShipStation, eBay and GA4. I built and own that automation layer. Ran both audits, wrote the reliability rules and built the QA monitor.

The problem

A QuickBooks sync error was caught and logged but never alerted anyone, so it could have sat for days. Auditing for that pattern turned up a whole class of them: catch blocks that logged and moved on, health checks reporting green while automated sends ran in dry-run mode and sent nothing, and network timeouts treated as clean failures that risked double charges on retry. A later check went deeper. When the QuickBooks API went down for hours, the monitor reported QuickBooks healthy with zero failures, and 5 of 15 watched services could never turn the check red at all.

What I built

I set one rule across every service: each sync and runner catch block logs and also calls an alert. Around it I added rules from real incidents. A timeout is an UNKNOWN outcome that must be verified before any retry, so a flaky network can't double-charge a customer or double-send an email. A send launch is confirmed from the send log record by record, never from config or a health endpoint. Any allowlist that gates a user action re-reads the source of truth on each request, so it survives a restart.

Then I built a QA monitor that checks about 12 systems on intervals from 5 minutes to 6 hours, routes CRITICAL, WARNING and INFO alerts to one problem-detection channel and caps itself at 30 alerts an hour so a wide outage stays readable. Where it can, it heals: it reactivates stale ShipStation stores and sends missed WooCommerce transactional emails.

When the monitor missed a QuickBooks API outage, I swept 29 production services and every scheduled task, comparing what each job claimed with whether it had produced its own output. I repointed stale watches, made non-critical results visible instead of discarded, moved the QuickBooks check onto the real accounting API with a 20-second deadline so it goes red instead of hanging, and connected the restored services to the company repository so they deploy by commit SHA.

Decisions that mattered

  • A transport error is recorded as UNKNOWN and verified before any retry, because a timed-out charge may have succeeded on the server.
  • If a service does not deserve to be reported, I remove the watch; I never leave one that cannot fail.
  • After a reconcile run of my own put 161 delete buttons on a board-wide banner, audits that expose destructive actions became owner-scoped, date-floored and isolated on their own page.
  • A job that never wrote its own log did not fail, it never started, so I check for the artifact before reading any status field.

How the result was checked

Every fix was re-checked against output, not status. The new QuickBooks check was verified to go down on a timeout and deliver its alert. The scheduled job that had never started has produced a report on every run since, with a last run result of 0, and the restored monitor answers its health check with a verified 200.
